## 1. 独立审查发现的问题

旧链的 operator candidate 绑定：

- `libopapi_nn.so`，SHA-256 `e9b192…d17`；
- 旧模型候选 ID：`adapter-853fb8f4e3ec6437554c`；
- 旧报告状态：`generated_unverified`，曾取得 5 份远程响应收据。

但 hash-bound AsNumPy `bindings/python/CMakeLists.txt` 的 `_core` 只链接 `opapi`。只读 ELF、
动态符号及实际 loader 绑定检查进一步确认：

- `libopapi.so` 与 `libopapi_nn.so` 都导出 MatMul 两个 ACLNN 符号；
- `libopapi.so` 不依赖 `libopapi_nn.so`；
- 当前 `_core` 的 MatMul 符号实际来自 `libopapi.so`；
- 简单追加 `opapi_nn` 会引入重复符号、`--as-needed` 和加载顺序歧义，还可能改变其他 NN
  接口的提供者。

因此“真实 NPU 测试能运行”不足以证明旧候选所绑定的 DSO 被复用。旧候选保留为审计历史，
但不再是可继续推进的 Adapter 候选。

### 2.2 MatMul 调用形式与 fallback 边界收紧

GapSpec 只审计两个位置参数。旧生成结果仅按值判断，无法区分
`matmul(a, b)` 与 `matmul(x1=a, x2=b)`，会把未审计 keyword 形式静默纳入 native 路径。

新的 semantic review 与 route Skill 明确要求：

- 只有恰好两个 positional arguments、且对象/秩/dtype/非空/内维/C-contiguous 全部满足时
  才允许 native；
- keyword、1-D、batched、broadcast、mixed dtype、empty 和 non-C-contiguous 必须保留
  既有 host fallback；
- 使用保留原 `(x1, x2)` 签名的私有 host 函数和可观察调用形式的公开 wrapper，非 native
  调用继续由原签名函数处理 Python 参数绑定与错误语义；
- qualification 必须分别证明上述越界等价类没有调用 native，而不能只证明一个正向样例。

### 2.3 模型传输与 prompt 投影

- official exact-edit 路由继续使用严格 SSE 聚合、有限响应体、请求/响应哈希和机械重建；
- `thinking` 保持 disabled，`reasoning_effort` 从 `minimal` 收紧为 `none`，避免隐藏推理耗尽
  exact-edit 内容预算；
- 完整 10 文件仍由本地 plan 读取和哈希绑定，但 `direct.py` 的远程投影只发送真正需要的

## 8. SSE keep-alive 与单请求 deadline 修复

linkage-v2 第一次续接重试在 `HTTPResponse.read(MAX+1)` 内等待 chunked HTTP EOF。网关已经发送
SSE `[DONE]`，但保持连接复用；客户端把完整应用层响应误判为传输挂起。修复后：

- `stream=True` 逐行读取有界 SSE entity body；只有完整空行终结的单一
  `data: [DONE]` 事件才停止，不接受正文中的 marker 或半个事件；
- DONE 检测使用常量状态，不按事件行数累积小对象；3 MiB 总响应边界与严格 SSE decoder 保留；
- 回执的 `response_body_sha256` 绑定实际消费到完整 DONE 事件的 body bytes；
- HTTP 连接建立前创建 monotonic deadline，流读取每轮把底层 socket timeout 收紧到剩余时间，
  并在每行后复核；持续 heartbeat/reasoning 不再无限刷新单次请求窗口；
- 真实 loopback HTTP/1.1 chunked keep-alive、malformed SSE、oversize 和总 deadline 均有回归。

修复后的真实端点验收把同一正式 Adapter 单轮窗口设为 10 秒：readiness 仍先取得 HTTP 200，
随后长 exact-edit 在整条命令约 13.35 秒时以 `LlmTransportError` 失败关闭，没有等到旧的
socket inactivity 重置周期，也没有创建输出目录。这证明 wall-clock 门禁已进入实际传输路径，
不是只对 loopback 测试生效。

修复后真实正式请求不再卡在 EOF：一轮在约 78 秒内返回 HTTP 200 与一份回执，并明确失败为
`product.cpp` 空 content。带安全的仅计数诊断进一步观察到：一次 `product.cpp` 回复包含
717 字符 final content；随后 `direct.py` 回复包含约 29,815 字符 reasoning、0 字符 final content，

正式三次重试又暴露旧 timeout 只是 socket inactivity timeout；7 分钟后人工中断，没有发布输出。
